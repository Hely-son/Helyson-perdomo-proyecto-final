**Revisión estática (S1 y precisión 1).** Archivos revisados: `app.ts`, `products.routes.ts`, `products.controller.ts` y `products.service.ts`.
- `app.ts` monta `requireAuth` en `[/api/v1/products, /api/v1/orders]`, después `testRouter` y por último el router de productos en `${API_PREFIX}/products`. Todas las rutas de productos quedan bajo el prefijo protegido y no hay ninguna fuera de él.
- `products.routes.ts` usa rutas relativas y registra `GET /alerts` antes que `GET /:productId`. No hay rutas `delete` ni `all`.
- El controlador solo serializa la respuesta y no aplica RN-09.
- El servicio hace una sola llamada `findMany` con `where { isActive: true, currentStock: { lte: db.fields.minStockAlert } }` y `orderBy [{ name: 'asc' }, { id: 'asc' }]`. El filtro se aplica en PostgreSQL mediante una referencia de campo de Prisma, sin SQL embebido. Después solo se hace `rows.map(toProduct)`, sin filtrar en JS. El orden es determinista: por nombre y, en caso de empate, por id.

**Registros `PrismaClientKnownRequestError` en `auth-guard.test.ts`.** Aparecen exactamente dos líneas, tanto en la suite completa como ejecutando ese archivo solo (43/43):
- `PrismaClientKnownRequestError GET /api/v1/products`
- `PrismaClientKnownRequestError GET /api/v1/products/alerts`

Las produce el `test.each(PROTECTED)` "ESC-29 parcial" con token válido. En esa suite, Prisma apunta a `127.0.0.1:9`, un servidor inexistente. Con token válido, las dos rutas llegan al servicio y la consulta falla con 500, lo que esa prueba admite porque solo exige "no 401". La línea de `/alerts` es nueva: antes la ruta caía en `/:productId` y respondía 422. La de `/products` corresponde a `listProducts` desde TK-03.1 (conclusión del análisis estático: no ejecuté la línea base).

En esa suite, `captureOutput` solo envuelve las peticiones D4a a `/__qa/*`. Por tanto, cualquier petición que llegara a un servicio de productos dejaría una línea visible. Que haya solo dos confirma que ninguna petición sin token, con token inválido o expirado (ESC-27, ESC-28) pasa de `requireAuth`. El formato cumple D4a: nombre del error, método y ruta sin query. No incluye `message`, stack ni `meta`, porque el manejador escribe `${name} ${method} ${baseUrl}${path}`. No es un defecto; la evidencia de éxito de ESC-29 está en alerts A13, contra la base real.

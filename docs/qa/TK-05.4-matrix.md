## Verificación de la fase 1 de lo que no puede ejecutarse sin la UI

- La parte de backend de ESC-12 se comprobó con un spec descartable (ya eliminado) contra el backend de E2E: el cliente E2E se identifica con `955500123`, el catálogo lista `QA TK-05.4 chat fixture` como `N) QA TK-05.4 chat fixture - $10.00`, `N` y `2` dejan `Tu carrito:\n- QA TK-05.4 chat fixture × 2…`, y una sesión nueva responde "Tu carrito está vacío." con un `sessionId` distinto. ## Brechas conocidas

Observaciones de la fase 2 (no bloqueantes):
- `src/chat/phone.ts` acepta como separadores espacio, guion y punto, y rechaza localmente cualquier otro carácter no numérico con "Usa solo dígitos en el teléfono." (mensaje no definido en la spec; no contradice §6.3 A y no envía la petición). La spec 05 §6.1/DP-01 también admite paréntesis como separador del backend, y §6.3 A habla de "separadores permitidos": un valor como `(9) 4907 6876` se rechaza en el simulador aunque el backend lo normalizaría. No está en ESC-56; decisión del coordinador si se alinea.
- El texto de `SESSION_INVALID` se elige por `code` y está fijado en el frontend con el texto del contrato; es compatible con el contrato y con la prueba QA-05.4-02, pero no muestra el `message` de la API si este cambiara.

- Separadores en el teléfono (spec 05 §6.3 A, "con o sin separadores permitidos"): no está en la tabla de ESC-56, no se prueba aquí; la normalización con separadores está cubierta en el backend (ESC-01..ESC-08, ESC-21).
- Entradas con caracteres no numéricos en el campo: la spec no define el mensaje local; no se prueban.
- ESC-08 (expiración con backend real) y CA-16: TK-05.5.

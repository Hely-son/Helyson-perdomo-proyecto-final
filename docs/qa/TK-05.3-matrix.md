## Interfaz bajo prueba (aprobada en la puerta 1)

```ts
createOrderService({ prisma }): OrderService
confirmOrder({ customerId, items: [{ productId, quantity, shownUnitPrice }] })
  → { ok: true,  order: { id, orderNumber, status: 'PENDING', totalAmount, items: [{ productId, quantity, unitPrice }] } }
  | { ok: false, rejections: [ { productId, reason: 'PRODUCT_INACTIVE' }
                              | { productId, reason: 'STOCK_INSUFFICIENT', availableStock }
                              | { productId, reason: 'PRICE_CHANGED', currentUnitPrice } ] }
```

**Tipo de los importes (precisión 1, confirmado).** `shownUnitPrice`, `unitPrice`, `currentUnitPrice` y `totalAmount` son **`string` con exactamente dos decimales** (`"100.00"`, patrón `^\d{1,10}\.\d{2}$`). Es el tipo de la columna `numeric(12,2)` (`backend/prisma/schema.prisma`: `price`, `unit_price`, `total_amount` `Decimal @db.Decimal(12, 2)`), del esquema `Money` del contrato (`docs/openapi.yaml`, `Money`/`MoneyInput`), de `ProductService` (`price.toFixed(2)` en `toProduct` y `listCatalog`) y del catálogo del chat (`price: string`). Nunca `number`: las pruebas exigen `typeof === 'string'` y el formato, y el total se compara con una suma exacta en centavos (BigInt) y con `total_amount::text` de la base, con importes elegidos para que un cálculo flotante o un redondeo previo falle (`1234567.89`, `0.07`, `19.99`). La aritmética del total debe ser decimal (por ejemplo `Prisma.Decimal`) o en enteros de centavos. Las cantidades (`quantity`, `availableStock`) y los identificadores son `number` enteros. **Sin conflicto con la interfaz ni con la spec.**

Forma exacta del resultado: las pruebas exigen las claves `id, items, orderNumber, status, totalAmount` en el pedido (D-01) y comparan los rechazos con `toEqual` exacto (sin claves adicionales; `PRODUCT_INACTIVE` no lleva `availableStock`). La spec no fija el orden de la lista de rechazos ni el de los ítems (D-01): las pruebas los ordenan por `productId` antes de comparar.

**Cómo reconocen las pruebas "el descuento condicional"** (necesario para el orden de bloqueo, las pausas de ESC-11 y la inyección de P2034): una llamada de la transacción a `product.updateMany` o `product.update` con `currentStock` en `data`, o un `UPDATE products` en SQL raw. Si el backend usa otra forma, las pruebas de orden y de pausa lo señalarán (el descuento no se reconoce) y habrá que acordarlo, no forzar el código.

## Condiciones obligatorias de la puerta 1

### A · Bloqueo de la fila y validación con datos vigentes

| Exigencia | Pruebas |
|---|---|
| El descuento es condicional y atómico, no una lectura previa seguida de escritura | "condición A · el stock baja de 10 a 5…" (stock final 3: una lectura previa daría 8); "condición A · el stock baja a 1…" (disponible vigente) |
| Estado activo, disponibilidad y precio se evalúan con datos vigentes al obtener el bloqueo | Las tres pruebas "condición A" y "ESC-11 (a)": el cambio se confirma con la confirmación ya en curso, antes del descuento, y el resultado debe reflejarlo |
| El precio se lee después del descuento, sobre la fila ya bloqueada | "descuento condicional · antes del primer descuento no hay lecturas de products…" (estructura) y ESC-11 (a) (comportamiento: una lectura previa al bloqueo vería 100.00 y crearía el pedido) |
| ESC-11 con un cambio de precio concurrente real contra PostgreSQL | ESC-11 (b): una segunda conexión espera el bloqueo (`pg_stat_activity`, `wait_event_type = 'Lock'`), no termina, y el pedido guarda el precio coherente con la comparación; ESC-11 (a) para el cambio ya confirmado |
| Orden ascendente de `productId` | "orden · entrada desordenada 7, 2, 5" (→ 2, 5, 7) y "orden · F-1 paso 3" (también con un ítem rechazado) |
| Si algún producto es rechazado, ningún descuento ni inserción queda persistido | ESC-04, ESC-05, ESC-06, ESC-07, ESC-08, ESC-11 (a) y variantes: comprueban el stock de **todos** los productos del pedido y la ausencia de pedido e ítems (`expectNothingPersisted`) |

Nota de nivel: la fase 1 pedía la prueba de orden como **U**. Un fake en memoria obligaría a prescribir qué llamadas de Prisma hace el servicio (modelo, SQL raw, nombres de métodos), así que se implementó como **I con espía sobre Prisma real**, que observa las sentencias reales sin imponer la forma. La prueba sigue sin necesitar ganchos de producción.

### B · Reintentos P2034

| Exigencia | Pruebas |
|---|---|
| (a) P2034 transitorio seguido de éxito → exactamente un pedido | ESC-12 (a); frontera con tres P2034 y éxito en el cuarto |
| (b) cuatro P2034 consecutivos → error y nada persistido | ESC-12 (b): 4 intentos exactos, error con `code: 'P2034'` |
| (c) un error que no es P2034 no se reintenta | Condición B (c): `Error` genérico, P2002 y P2025, un solo intento |

El P2034 se lanza **después** del primer descuento real de cada intento, de modo que el stock descontado en el intento fallido debe revertirse y no duplicarse en el reintento (stock final 8/4, no 6/3).

### C · Aislamiento de la secuencia `order_number_seq`

- La secuencia es global y no transaccional. El arnés `test:db` (`reset-before-each.ts` → `resetDatabase`, `TRUNCATE … RESTART IDENTITY` + `ALTER SEQUENCE order_number_seq RESTART WITH 1`) la reinicia **antes de cada test**, y `globalSetup` recrea la base una vez por ejecución; `order-number.test.ts` (TK-00.3) además llama a `resetDatabase` en su `beforeEach`.

Decisiones P1..P4 de la puerta 1 (2026-11-27).

Criterio del PRD: **CA-12** (a) cancelar PENDING/PROCESSING restituye; (b) cancelar DISPATCHED/DELIVERED/CANCELLED es rechazado sin cambios; (c) la restitución ocurre una sola vez, también en cancelaciones repetidas o simultáneas.

Niveles: **U** unidad (Prisma doble) · **I** integración contra PostgreSQL real (`medsupply_test`, `npm run test:db`) · **C** concurrencia con conexiones reales (RNF-01, RNF-04).

IDs: **"ESC-14 (spec 02)"** (ajuste con `expectedStock` tras cancelar) no es el ESC-14 de la spec 04 (ROLLBACK de la confirmación, ya cubierto en TK-05.3). Equivalentes con un único test: spec 04 ESC-26 ≡ spec 02 ESC-30; spec 04 ESC-28 ≡ spec 02 ESC-31.

## Interfaz que asumen las pruebas (puerta 1)

| Elemento | Comportamiento asumido |
|---|---|
| Operación | `changeOrderStatus(orderId: number, target)` en el objeto que devuelve `createOrderService({ prisma })` |
| Éxito | `{ id, orderNumber, status }` exactamente (sin ítems ni total); `status` = destino |
| Errores de dominio | `AppError(404, 'ORDER_NOT_FOUND')` si el pedido no existe; `AppError(409, 'INVALID_ORDER_TRANSITION')` para transición no permitida, mismo estado (D-06) o carrera perdida. Sin cambios en pedido ni stock |
| Entrada inválida (P3) | Destino `PENDING` o fuera del enum (también minúsculas, `null`, número, objeto) → `OrderInputError`, sin tocar la base (ni transacción ni consultas) |
| Avance | Actualización condicional al origen esperado; el stock no cambia (D-07) |
| Cancelación | Una transacción: `updateMany` condicional `status IN (PENDING, PROCESSING)` → `CANCELLED`; 0 filas → 404/409 y stock intacto; 1 fila → incrementa cada ítem en orden ascendente de `productId`, también si el producto está inactivo |
| Reintentos (P4) | Cancelación entera ante `P2034`: 1 intento + hasta 3 reintentos (4 en total); agotados, el error se propaga. Otros errores no se reintentan. Regresión de P4: `tests/db/orders-confirm-retry.test.ts` (no se modifica) debe seguir verde |
| Prisma doble (U) | El servicio usa `order.updateMany` (o `update`/`findUnique`/`findFirst`/`count`), `orderItem.findMany`, `product.update`/`updateMany` con `currentStock: { increment }` y `$transaction`. SQL raw no está soportado por el doble: si el ingeniero lo usa en la cancelación, se acuerda con QA y se ajusta el doble |
| Forzadas (C) | Suponen lo que fija la spec: la primera escritura de la cancelación es la actualización condicional del pedido (F-5 2.1) y la restitución recorre los productos en orden ascendente (D-05) |

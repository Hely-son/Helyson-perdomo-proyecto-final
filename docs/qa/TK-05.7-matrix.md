## Interfaz pública mínima que asumen las pruebas (para revisión del usuario)

Archivo de implementación futura: `backend/src/modules/chat/session-store.ts`. Genérico en estado de conversación y carrito (valores opacos); sin HTTP, sin Prisma, sin tipos del FSM.

```ts
export interface ChatSession<TState, TCart> {
  readonly id: string;           // UUID (crypto.randomUUID)
  readonly customerId: number;   // cliente identificado
  state: TState;                 // estado de conversación (opaco)
  cart: TCart;                   // carrito (opaco)
  lastProcessedAt: number;       // ms epoch (Date.now) del último mensaje procesado con éxito
}

export type ProcessResult<R> =
  | { status: 'processed'; result: R }
  | { status: 'invalid' };       // inexistente o expirada: el manejador NO se invoca

export class ChatSessionStore<TState, TCart> {
  constructor(options: { ttlMinutes: number });  // ttlMinutes viene de env.chatSessionTtlMinutes
  create(input: { customerId: number; state: TState; cart: TCart }): ChatSession<TState, TCart>;
  get(id: string): ChatSession<TState, TCart> | undefined;   // undefined si no existe o expiró (la descarta); NO renueva
  process<R>(
    id: string,
    handler: (session: ChatSession<TState, TCart>) => Promise<R> | R,
  ): Promise<ProcessResult<R>>;  // en serie por sesión; el manejador muta session.state / session.cart
  startSweep(): void;            // setInterval fijo de 1 minuto (D-1)
  stopSweep(): void;             // limpia el temporizador (D-2)
  readonly size: number;         // sesiones en memoria (observa el barrido y los descartes)
}
```

Convenciones que fijan las pruebas:
- Reloj: el almacén lee `Date.now()`; las pruebas lo controlan con `jest.useFakeTimers` (no hay reloj inyectado, para mantener la interfaz mínima). El TTL se inyecta en minutos.
- `create` fija `lastProcessedAt` a la hora de creación.
- `process`: si la sesión no existe o la inactividad es estrictamente mayor que el TTL (comprobada cuando le llega el turno al mensaje, D-3a), responde `{ status: 'invalid' }`, no invoca el manejador y descarta la sesión. Si el manejador termina bien, renueva `lastProcessedAt` y responde `{ status: 'processed', result }`. Si el manejador lanza o rechaza, el error llega a quien llamó, no renueva (D-3b), no descarta una sesión vigente y el siguiente mensaje en cola sigue su curso.
- Un mensaje de otra sesión no espera; dentro de una sesión el orden es el de llegada.
- `get` no renueva el plazo (DP-06: solo lo renueva el procesamiento de un mensaje).

## Cobertura y límites

- Este test unitario del mecanismo en serie no crea pedidos (ESC-35 es de TK-05.5).
- No fijado por la spec y no probado: si la hora renovada es la del inicio o la del fin del manejador (los tests usan manejadores instantáneos, salvo los de D-3a/D-3b, cuyo resultado no depende de ello). Queda a criterio del ingeniero; sugerencia: hora al terminar con éxito.
- No probado: que el temporizador del barrido use `unref()` (no es observable con fake timers); es una buena práctica del ingeniero para no retener el proceso.
- No cubierto por este ticket: conexión del barrido a `server.ts` y respuestas HTTP `SESSION_INVALID` (TK-05.1); FSM y carrito (TK-05.1, TK-05.2).

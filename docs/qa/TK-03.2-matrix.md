# TK-03.2 · Matriz QA (análisis y verificación)

Fuentes: TK-03.2 (`backlog/US-03_catalogo_inventario.md`, US-03 crit. 3–4), spec 02 F-5, §7, §8.1 (`adjustProductStock`), §9, §11.2 y §11.5 (DP-02, DP-06), ARCHITECTURE "Ajuste de stock", contrato `docs/openapi.yaml` (`PATCH /products/{productId}/stock`, `adjustProductStock`, schema `AdjustStockRequest`; respuestas 200 `Product`, 400, 401, 404, 409, 422) y los criterios AC-1..AC-14 aprobados en la puerta 1 (2026-11-25), con la decisión D1 (ESC-13 por fixture) y D3 (sin revisión de seguridad independiente; QA verifica autenticación, validación estricta, protección de la ruta y que solo cambie `current_stock`).

Criterio del PRD: **CA-13**. Niveles: **I** integración contra PostgreSQL real, `medsupply_test` (`npm run test:db`) · **C** concurrencia: peticiones HTTP reales en paralelo contra un servidor en puerto efímero (`withRealServer`) y PostgreSQL real (RNF-01, RNF-04).

## Interfaz que asumen las pruebas

| Elemento | Comportamiento asumido |
|---|---|
| Ruta | `PATCH /api/v1/products/:productId/stock`, montada en el router de productos, **después** de `requireAuth`; `productId` validado como en TK-03.1 (422 si no es entero ≥ 1) |
| Cuerpo | `AdjustStockRequest` estricto: `newStock` y `expectedStock` enteros 0..2147483647, ambos requeridos, sin campos extra. JSON inválido → 400 (`jsonBody`) |
| Respuesta | 200 `Product` sin envoltorio, igual a la fila (`expectProductMatchesRow`). Errores con el esquema `Error` (`tests/helpers/error-response.ts`) |
| Efecto | Solo cambian `current_stock` (y `updated_at`). `newStock === expectedStock` → 200. No se exige nada sobre `updated_at` |
| Concurrencia | Precisión aprobada: `prisma.update` con `where { id, currentStock: expectedStock }` y `data { currentStock }`; ante P2025, `findUnique` para distinguir 404 de 409. Las pruebas no exigen transacciones ni bloqueos: el bloqueo de las variantes "intercalado forzado" lo pone el arnés |

**Revisión estática (D3).** Archivos revisados: `products.routes.ts`, `products.schemas.ts`, `products.service.ts` y `products.controller.ts`.
- `app.ts` no cambió: la ruta `PATCH /products/:productId/stock` queda bajo el prefijo protegido por `requireAuth`.
- El cuerpo se valida con `z.strictObject` sobre `stockInt`: entero de 0 a 2147483647, sin conversión de tipos. El id se valida con `productIdParams`.
- El servicio hace una sola llamada `update` con `where { id, currentStock: expectedStock }` y `data { currentStock: newStock }`. `updated_at` lo pone Prisma (`@updatedAt`).
- La respuesta 200 sale de la fila que devuelve el `update`.
- Ante P2025 consulta con `findUnique`: si el producto no existe responde 404 `PRODUCT_NOT_FOUND`; si existe, 409 `STOCK_CHANGED`. Los demás errores siguen al manejador global.
- El mensaje del 409 difiere del ejemplo del contrato, que no es normativo; el esquema `Error` se cumple y lo exige `expectErrorResponse`.

Observaciones menores, que no bloquean:
- El comentario `/** Lo único que el servicio necesita de la base… */` quedó encima de `AdjustStockInput` y no de `ProductDb`.
- El backend no agregó pruebas técnicas propias; las de aceptación cubren los casos de borde de la spec.

## Interfaz que fijan las pruebas (el implementador la respeta)

| Módulo | Exporta / comportamiento |
|---|---|
| `src/auth/session.ts` | `interface Session { token: string; expiresAt: string; operatorName: string }` · `parseStoredSession(raw: string \| null): Session \| null` (JSON corrupto, incompleto, `token` vacío, tipos erróneos o `expiresAt` ilegible → `null`; una sesión vencida se lee igual) · `isSessionValid(session: Session \| null, now: number): boolean` (`Date.parse(expiresAt) > now`; `null` o ilegible → `false`). No decodifica el JWT |
| `src/auth/session-store.ts` | `SESSION_STORAGE_KEY = 'medsupply.session'`; en el almacenamiento, JSON `{ token, expiresAt, operatorName }` · `interface StorageLike { getItem; setItem; removeItem }` · `createSessionStore(storage: StorageLike)` → `{ getSession(); setSession(s); clearSession(reason: 'expired' \| 'logout' \| 'unauthorized'); subscribe(fn): () => void; consumeEndReason(): reason \| null }` · `clearSession` es idempotente y notifica solo si había sesión · un valor corrupto al hidratar se elimina · el motivo se consume una sola vez · instancia por defecto `sessionStore` (usa `localStorage` en el navegador; **en Jest/node, sin `localStorage`, debe poder importarse y funcionar**) |
| `src/auth/guards.ts` | `resolveProtectedAccess(session, now)` → `{ kind: 'allow' }` \| `{ kind: 'redirect', to: '/login', reason: 'none' \| 'expired' }` · `resolveLoginAccess(session, now)` → `{ kind: 'redirect', to: '/dashboard' }` \| `{ kind: 'form', clearExpired: boolean }` · `resolveUnknownRoute(session, now)` → `'/dashboard' \| '/login'`. Son puras: no limpian ni llaman a la API |
| `src/auth/errors.ts` | `isSessionLost(error: unknown, options: { auth: boolean }): boolean`: `true` solo si `error instanceof ApiError`, `auth === true` y `code === 'UNAUTHORIZED'` |
| `src/auth/login-validation.ts` | `validateLoginInput({ email, password })` → `{ email?: string; password?: string }` (`{}` si es válido; mensajes no vacíos, texto libre) |
| `src/api/client.ts` | Se extiende: `ApiRequestOptions.auth?: boolean` · `SessionExpiredError` y `NoSessionError` (clases exportadas, distintas: ninguna es subclase de la otra) · `setSessionLostHandler(fn: ((reason: 'expired' \| 'unauthorized' \| 'none') => void) \| null)`. Con `auth: true`: sin sesión guardada, no llama a `fetch`, invoca el manejador con `'none'` (redirige a `/login`), lanza `NoSessionError`, no notifica a los suscriptores del almacén y no deja el motivo `'expired'` (es idempotente; no se fija si el manejador se repite); Bearer desde `sessionStore`; si la sesión venció, no llama a `fetch`, hace `clearSession('expired')`, invoca el manejador y lanza `SessionExpiredError`; `UNAUTHORIZED` → `clearSession('unauthorized')` y el manejador **una vez** aunque haya respuestas simultáneas, y propaga el `ApiError`. Sin `auth`, no envía el token ni toca la sesión. **Debe poder importarse en Jest: hoy `import.meta.env.VITE_API_BASE_URL` lanza `TypeError` en node (`import.meta.env` no existe)**; la base por defecto sigue siendo `/api/v1` |
| UI (E2E) | `/login`: campos con etiqueta exacta **"Email"** y **"Contraseña"**, botón **"Iniciar sesión"**; error local como descripción accesible del campo (`aria-describedby` de `Form.Item`); mensaje de credenciales **"Email o contraseña incorrectos."**; aviso de expiración que cumple `/sesi[oó]n[^.]*expir/i`, solo tras una expiración detectada · layout: nombre del operador visible y entrada de menú **"Cerrar sesión"** habilitada · `/dashboard` mantiene el encabezado "Alertas de stock" |

## Infraestructura E2E (D2, D3, D6)

- `playwright.config.ts`: `MEDSUPPLY_E2E_JWT_SECRET` (48 bytes aleatorios) y `MEDSUPPLY_E2E_OPERATOR_PASSWORD` (24 bytes) con `??=`, una vez en el proceso principal; los workers heredan el entorno. `JWT_SECRET` llega al backend por `webServer.env`. `globalSetup: './e2e/global-setup.ts'`. Se exporta `resolveTestDatabaseUrl()`.
- `e2e/global-setup.ts`: `spawnSync` sin shell de `backend/node_modules/.bin/tsx` sobre `backend/tests/e2e-support/upsert-e2e-operator.ts`. Al hijo solo le pasa por entorno `PATH`, `DATABASE_URL`, `E2E_OPERATOR_EMAIL`, `E2E_OPERATOR_NAME` y `E2E_OPERATOR_PASSWORD`.
- `backend/tests/e2e-support/upsert-e2e-operator.ts`: antes de conectarse valida que la base sea exactamente `medsupply_test` y que el email termine en `.test`; ya conectado, comprueba `current_database()`; hace `prisma.user.upsert` con `hashPassword` del backend; los mensajes son fijos. Queda fuera de `tsconfig.build.json` y de `backend/.dockerignore`.
- Operador E2E: `operador.e2e@medsupply.test`, con el nombre "Operadora E2E Ficticia" (`e2e/support/e2e-env.ts`).
- `e2e/support/session.ts` · `openLoginForm()`: antes de crear una espera de red (`waitForRequest`/`waitForResponse`), comprueba con `expect` que el formulario está a la vista. Sin esa comprobación, un test en rojo agotaba el timeout del test con la espera pendiente y Playwright 1.64.1 tardaba de 4 a 15 minutos en cerrarlo; con ella falla en unos 5 s.
- Orden: `cd backend && npm run test:db` (o `db:migrate:test`) y después `cd frontend && npm run test:e2e`, nunca a la vez.

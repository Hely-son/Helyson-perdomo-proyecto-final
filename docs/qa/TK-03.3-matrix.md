## Contrato de interfaz para `frontend-engineer` (fijado por las pruebas, D1)

**1. `src/api/products.ts`.** Todas las funciones usan `apiRequest({ auth: true })` y devuelven el cuerpo tal como llega (`ProductList` = `{ items }`; `Product`). Los ids se interpolan con `encodeURIComponent(String(id))` (S-3).

| Exporta | Petición |
|---|---|
| tipos `Product`, `ProductList`, `CreateProductRequest`, `UpdateProductRequest`, `AdjustStockRequest` | schemas homónimos del contrato |
| `listProducts(): Promise<ProductList>` | `GET /products` |
| `listStockAlerts(): Promise<ProductList>` | `GET /products/alerts` |
| `getProduct(id: number): Promise<Product>` | `GET /products/{id}` |
| `createProduct(body: CreateProductRequest): Promise<Product>` | `POST /products` |
| `updateProduct(id: number, body: UpdateProductRequest): Promise<Product>` | `PATCH /products/{id}`, cuerpo = exactamente `body` (DP-06) |
| `deactivateProduct(id: number): Promise<Product>` | `POST /products/{id}/deactivate`, sin cuerpo |
| `adjustProductStock(id: number, body: AdjustStockRequest): Promise<Product>` | `PATCH /products/{id}/stock` |

**2. `src/products/inventory.ts`** (lógica pura, sin React):

```ts
criticalProductIds(products: readonly Product[], alerts: readonly Product[] | null): ReadonlySet<number>
buildAdjustStockRequest(shown: Pick<Product, 'currentStock'>, newStock: number): AdjustStockRequest // { newStock, expectedStock: shown.currentStock }
classifyProductError(error: unknown): ProductErrorOutcome
runProductAction<T>(action: () => Promise<T>, reloadLists: () => unknown): Promise<ProductActionResult<T>> // nunca rechaza
type ProductErrorOutcome =
  | { kind: 'session' }                                   // UNAUTHORIZED, SessionExpiredError, NoSessionError
  | { kind: 'validation'; message: string }               // VALIDATION_ERROR: message del backend, sin cambios;
                                                          // MALFORMED_REQUEST: mensaje genérico propio (O-1)
  | { kind: 'conflict'; message: string; reloadLists: true }  // STOCK_CHANGED: mensaje propio que menciona el stock
  | { kind: 'not-found'; message: string; reloadLists: true } // PRODUCT_NOT_FOUND: mensaje propio que menciona el producto
  | { kind: 'technical'; message: string };               // resto: genérico, sin message, code ni detalles del servidor
type ProductActionResult<T> = { ok: true; value: T } | { ok: false; error: ProductErrorOutcome };
```

`criticalProductIds` cruza por `id`, sin comparar stock ni evaluar `isActive`. Con `alerts` en `null` devuelve un conjunto vacío.

`runProductAction` llama a `reloadLists` una vez ante un éxito, `conflict` o `not-found`, y ninguna ante `validation` o `session`. `validation` se muestra dentro del formulario, sin cerrar el modal ni perder los datos ingresados. Ante `technical` no se fija. La clasificación decide por `code`.

**3. Ruta.** El loader de datos va en la ruta hija directa `path: '/dashboard/products'` de la ruta de layout cuyo `loader` es `protectedLoader` (W1). La forma de esa ruta la exige además el montaje de TK-01.4, que sustituye `child.loader` por `path` (R1).
- Las dos lecturas salen en paralelo: las dos peticiones están en curso antes de que llegue cualquier respuesta (ESC-41).
- El mecanismo de carga es libre: `HydrateFallback`, `useNavigation` o carga diferida (R2).
- Si falla `listStockAlerts`, la tabla se muestra y no se lanza ningún error. Si falla `listProducts`, la pantalla pasa a error técnico.

**4. HTML observable de la página:**

| Elemento | Contrato |
|---|---|
| Fila | `<tr … data-row-key="{id}">` (`Table` de antd con `rowKey="id"`) |
| Fila resaltada | clase `is-stock-critical` en el `<tr>`, solo para los ids de `criticalProductIds` |
| Estado | texto `Activo` / `Inactivo` en la fila |
| Stock | entero en su propia celda (`<td …>7</td>`) |
| Cargando | `/ant-spin-spinning\|ant-skeleton\|aria-busy="true"\|cargando/i` |
| Catálogo vacío | `/cat[aá]logo[^<]*vac[ií]o\|no hay productos/i` |
| Error técnico | `/no se pudo cargar el cat[aá]logo\|no se pudieron cargar los productos/i`, sin el `message` del servidor, `INTERNAL_ERROR` ni `fetch failed` |
| Alertas no disponibles | `/stock cr[ií]tico[^<]*no (est[aá] )?disponible/i` |

**5. Selectores E2E (ESC-57).**
- En la fila: botones con nombre accesible `Editar` y `Ajustar stock`. Una fila inactiva no tiene ningún botón cuyo nombre contenga `activar`, ni de reactivación ni de desactivación (diseño aprobado en la puerta 1). En la página no hay botones `Reactivar`.
- Los formularios son modales (`role="dialog"`), con los campos etiquetados exactamente `Precio` (editar) y `Nuevo stock` (ajustar). El botón de envío empieza por `Guardar`, `Ajustar`, `Confirmar` o `Aceptar`.
- Después de una operación con éxito, el modal se cierra y se recargan `GET /products` y `GET /products/alerts`.
- La edición no envía `isActive` ni `currentStock`. El ajuste envía `{ newStock, expectedStock: <stock mostrado> }`.

  - El montaje de TK-01.4 devuelve `null`, pero nunca renderiza la página (R1), así que hoy no hay impacto.
  - Si una prueba futura la renderizara con ese montaje, fallaría con `TypeError`.
- **F-2:** tras una operación correcta, la recarga es una revalidación, no una navegación, y no muestra indicador: la tabla anterior sigue visible hasta que llegan las listas. ESC-41 pide indicador "mientras llega `listProducts`" al abrir la pantalla, y eso se cumple. Mejora opcional de experiencia de uso.

Esos comportamientos quedan cubiertos solo de forma indirecta: E57 para la edición, y W2 y el sondeo para la sesión.

## Interfaz que asumen las pruebas (el implementador la respeta)

| Módulo | Exporta / comportamiento |
|---|---|
| `src/app.ts` | `createApp(options: CreateAppOptions): Express` con `CreateAppOptions { auth: { jwtSecret: string; jwtExpiresIn: string }; prisma: PrismaClient; testRouter?: Router }`. `jwtExpiresIn` con el formato de `JWT_EXPIRES_IN` (`3s`, `8h`…). El middleware Bearer se monta en `/api/v1/products` y `/api/v1/orders` (D2) **antes** que `testRouter`, de modo que una ruta de `testRouter` bajo esos prefijos queda protegida. `testRouter` sigue montándose bajo `/api/v1`, antes de los manejadores 404 y de errores |
| Middleware Bearer | Stateless (ARCHITECTURE "Autenticación"; D1): valida firma HS256 (`algorithms: ['HS256']`) y `exp`; **no consulta la base**. Acepta `sub` como cadena decimal del id (RFC 7519 §4.1.2), que es como lo firman las pruebas; el token que emite `login` debe ser aceptado por el propio middleware (ESC-23, ESC-28 b). Las pruebas H le pasan un `PrismaClient` apuntado a un servidor inexistente |
| `src/modules/auth/password.ts` | `BCRYPT_COST` (`10`, sin cambios) · `DUMMY_PASSWORD_HASH: string` (D3: hash bcrypt fijo, costo `BCRYPT_COST`) |
| `src/config/env.ts` | Sin cambios: `loadConfig` aplica `8h` por defecto (ESC-31 los conecta con `createApp`) |
| `src/server.ts` | Puerto ocupado → mensaje controlado en stderr, `exit 1`, sin stack (D4b) |
| Registro de 500 (D4a) | En stderr solo `err.name` y método + ruta (`baseUrl + path`, sin query); por `console.error` o `process.stderr.write`. Respuesta HTTP sin cambios (`INTERNAL_ERROR`, "Ocurrió un error inesperado.") |

Las pruebas no usan `tests/helpers/app.ts` (`createTestApp`): llaman a `createApp` con un secreto de prueba propio para poder firmar tokens en el test. Los tokens se firman con `node:crypto` (`tests/helpers/jwt.ts`), independiente de la biblioteca de la implementación.

## Procedimiento de QA-00.6-D07 (fase 2, obligatorio)

`dct` = `docker compose -p medsupply-tk011-qa -f docker-compose.delivery.yml`, desde la raíz. `S` = scratchpad de la sesión de QA.

**Prohibido:** `down -v`, `docker volume rm`, `docker … prune` o cualquier limpieza global. No detener proyectos ajenos: si el puerto 8080 está ocupado (`docker ps --filter publish=8080`), `Bloqueado` y se informa.

1. `dct up -d --build --wait` → exit 0. `dct ps -a` → `migrate` y `seed` `Exited (0)`; `db`, `backend`, `nginx` en marcha.
2. Cuerpo válido en `S/d07-ok.json` (permiso 600), armado desde `SEED_OPERATOR_EMAIL` y `SEED_OPERATOR_PASSWORD` del `.env` con `node --env-file=.env -e …`, sin imprimir valores.
3. `curl -s -o S/d07-ok.out -w '%{http_code}' -H 'Content-Type: application/json' --data-binary @S/d07-ok.json http://127.0.0.1:8080/api/v1/auth/login` → `200`. Se registran solo el status y las claves (`Object.keys` del cuerpo y de `operator`); **nunca el token**.
4. Inmediatamente: `dct exec -T db sh -c 'psql -U "$POSTGRES_USER" -d postgres -tAc "select a.usename, a.datname, r.rolsuper from pg_stat_activity a join pg_roles r on r.rolname = a.usename where a.datname = '"'"'medsupply'"'"' and a.pid <> pg_backend_pid()"'` → toda fila con `usename = $APPU` y `rolsuper = f`; ninguna con el superusuario.
5. Repetir 2–4 con `S/d07-bad.json` (mismo email, contraseña ficticia incorrecta) → `401` y `code = INVALID_CREDENTIALS`; misma conclusión en `pg_stat_activity`.
6. Borrar `S/d07-ok.json`, `S/d07-bad.json` y las salidas (`rm` de esos archivos concretos).
7. `dct down` **sin `-v`**. El volumen `medsupply-tk011-qa_pgdata` queda y se informa.

Resultado esperado: (3) 200 con claves `expiresAt, operator, token, tokenType` y `operator` `email, id, name`; (5) 401 `INVALID_CREDENTIALS`; (4) y (5) solo `$APPU` no superusuario. CI: excepción aprobada (D5), evidencia local contra PostgreSQL 16; CI pendiente por TK-00.7.
